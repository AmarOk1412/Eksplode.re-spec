# Implementation Plan: Player Customization, New Powers, Sound and Developer Mode

**Branch**: `003-customization-powers-audio` | **Date**: 2026-10-22 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/003-customization-powers-audio/spec.md`

## Summary

Five increments on top of the existing workspace (`core`, `bots`, `net`, `cli`, `web`, `web-render`), delivered in the order requested:

1. **Customization**: a `Look` (main colour, gender look, head and face accessory) travels with `Join`/`SetLook`, is validated and colour-deduplicated by the host, shown to everybody through the lobby message, saved in the browser, edited with a live preview, and drawn on the in-match sprites.
2. **Powers and maluses**: `core` gains the roller/flame naming (existing speed and range), the rare **punch** (bombs hop square by square to the first free square), and three timed maluses (slow, hyper speed, small bomb). Items are decided **when a block is destroyed** from a per-power drop table, so the table can change at run time. The terminal client gets the same rules (letters, status line, a punch key).
3. **Semi-3D lobby**: the character cards of the lobby are drawn as isometric cubic characters (cube head with a pixel face, cube body, accessories, idle bob) by `web-render`, following the reference image.
4. **Noise, music and settings**: generated sound effects and two looping tunes synthesised in the browser (no recordings), a settings panel with music and effects volume and mute, stored per device.
5. **Developer mode**: `--dev` on the server (and on `eksplode-re-cli host`) enables owner-only commands to pause bots and set per-power drop chances.

No new third-party dependency is needed: appearance and developer messages are additive to protocol version 1, audio uses the browser's built-in synthesis, and the rest is existing crates.

## Technical Context

**Language/Version**: Rust 2021 (stable in CI, nightly locally), `wasm32-unknown-unknown` for `web-render`; ES2022 JavaScript (modules) for the page.

**Primary Dependencies**: existing only: `serde`/`serde_json`, `tungstenite`, `ratatui`, `ctrlc`. Browser built-ins: Web Audio, `localStorage`, canvas 2D. No audio files and no JS libraries.

**Storage**: browser `localStorage` for the look and the audio settings (per device, versioned keys). The server keeps looks, the drop table and the bot pause only in memory for the life of the process.

**Testing**: `cargo test --workspace` (core scenarios for punch, maluses and drops; net loopback and WebSocket tests for looks and dev commands; web-render tests for look skins and the 3D portrait; docs and consistency tests), `node --test` (look editor state, settings, sound mapping and music scheduling against a fake audio context, dev panel reducer), `scripts/pty-enter-check.py`, `scripts/browser-smoke.mjs` extended with screenshots of the editor, the 3D lobby and the dev panel.

**Target Platform**: Linux server and terminal; evergreen browsers (Chromium, Firefox) with WebAssembly and Web Audio. Everything works silently when audio is missing.

**Project Type**: Cargo workspace with a server, a terminal client and a web page (existing).

**Performance Goals**: 60 fps in the match and in the animated lobby; p95 key-to-snapshot at most 200 ms (SC-010); audio scheduling never blocks drawing.

**Constraints**: protocol stays version 1 (additive fields with defaults, unknown values replaced by defaults, never an error for others); wasm at most 300 KB and the page at most 500 KB (today 157 KB and 171 KB); all sounds generated by code, no third-party samples; `unsafe` only in `crates/web-render/src/ffi.rs`; no game rules in JavaScript.

**Scale/Scope**: 4 participants, 8 powers, 10 colours, 2 gender looks, 2 accessory places (4 choices each), 2 tunes, 9 sound effects.

## Key Design Decisions (details in research.md)

- **Look outside `core`.** The look is cosmetic, so it is carried by `net` and never influences a rule. The lobby message carries four looks next to the four slots.
- **Lenient wire decoding.** `look` is read as loose JSON and turned into a valid `Look` field by field, so an old page, a typo or a hostile message only ever produces a default look for that sender.
- **Colour conflicts are the host's job.** The first participant in a slot keeps their colour; a later one gets the next free colour in palette order and an `Error{LookAdjusted}` notice.
- **Items are decided at destruction.** `hidden_powerups` disappears; `GameState.drops` (a `DropTable`) is rolled once per destroyed block with the seeded RNG. This gives developer mode a live table and keeps the observation unchanged (hidden items were never visible anyway).
- **Punch is a flight, not a teleport.** A punched bomb keeps its fuse, hops one square every 2 ticks, is immune to flames in the air, and lands on the first square without block, wall, player or bomb; fallbacks are defined for the edge of the arena.
- **Maluses are timed state on the player.** One slot, newest replaces older, 10 s, speed computed from the base cooldown at move time so bonuses and maluses never fight over one number.
- **Semi-3D is polygons.** The lobby character is built from quads in the same command buffer (isometric cubes with a pixel face texture), so no new rendering technology is needed.
- **Audio is code.** A tiny synthesiser (oscillators, noise bursts, envelopes) and a lookahead step sequencer produce every sound and both tunes from fixed seeds, so output is reproducible, tested with a fake context, and free of copyright concerns.
- **Dev mode is explicit and owner-only.** Off unless `--dev`; every command is checked on the server; a warning is printed at start-up.

## Complexity Tracking

| Item | Why needed | Simpler alternative rejected because |
|------|------------|--------------------------------------|
| Principle VI scope: looks, 3D lobby cards, sound and the dev panel exist only in the web page | They are presentation or developer tooling, not gameplay; the terminal cannot show 3D art or play generated music in a meaningful way. Gameplay (powers, punch, maluses, drops) is fully in both clients, and `host --dev` gives the terminal host the dev rules | Duplicating cosmetic editors and audio in a terminal adds large cost for no rule parity benefit; the principle's text requires parity for gameplay features |
| Moving item decisions from arena generation to block destruction | A live developer drop table and per-power chances need the decision at destruction | Keeping hidden items fixed at generation cannot honour a table changed mid-match (FR-028) |
| Two new static routes (`/look.js`, `/audio.js`; the dev panel stays inside `app.js`) | Keeps `app.js` readable and each module testable in node | One 1500-line `app.js` is harder to test and review; still no build step or bundler |
| New wasm exports in `ffi.rs` | The look and the 3D portrait need data from JS into the module | Re-deriving looks in JS would duplicate rendering decisions the constitution keeps in `web-render` |
